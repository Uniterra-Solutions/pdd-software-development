# AP-008 · 失敗即整批回退

> 後續（2026-11-18）：本 plugin 已不再隨 skill 附腳本。下文提到的 checker 與 `scripts/` 路徑均已移除，其職責改由回合內的命令與閱讀承擔 —— 事故的教訓不變，當時的修正手段已過時。

## 一句話

同一個二百多步的遷移連續五次從**同一個 commit** 開始。每次跑一到兩小時；只要一步失敗就回退工作區到基線，已成功的部分全部丟棄。有一次五十五步只壞七步，另外四十八步的好工作一起被丟掉。

## Shape（技能的 Step 1 分類）

**形狀**：誤導性規則（misleading rule）

需求文件寫（計畫層，非技能層）：

> 改名只經決策圖，且只經一個命令

缺口：`skills/implement/references/subagent-dispatch.md` —— 技能沒有任何一句講「一個任務的多步失敗時，工作區要保留到什麼程度」；brief 的失敗協議因此由我臨場發明，而每一次發明都選了回退。

當時的讀法：「一個命令 ⇒ 結果必須全有或全無 ⇒ 失敗就回到命令執行前。」這句話講的是**一次呼叫的原子性**（不留半套狀態），不是**工作區歷史的原子性**（不留部分成果）。

## Step 2 — 反模式

```
### AP-008 · 失敗即整批回退

- 觸發：多步遷移中某一步失敗
- 錯誤動作：把工作區回退到基線，下一次從同一個 commit 重來
- 為何看起來合理：all-or-nothing 聽起來等於可驗證性；回退看起來比留半套保守
- 正確動作：保留已成功的部分並 commit 檢查點，只重做失敗的那幾步
- 可觀察徵兆：同一個任務連續多次從同一個 commit 開始
- 來源：一次多步遷移的五次嘗試
```

## Step 3 — 類別

**改進類別**：提示改進

**未採用**：`代碼改進`（沒有腳本說謊：套用呼叫的原子性是對的）、`資訊改進`（我不是不知道部分成果有價值）、`流程改進`（順序與結構沒問題，問題在 brief 的預設值）

## 落地

`skills/implement/references/subagent-dispatch.md` §5 增一條：brief 不得指示整棵樹回退；失敗時 commit 檢查點並只重做失敗的部分。`implement` 2.4.2。

## 回歸判準

第二次執行的起點必須是第一次留下的 `wip(...)` 檢查點，且失敗清單比第一次短。
