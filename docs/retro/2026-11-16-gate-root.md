# 九個乾淨的 unit 被同一個檢查器判成九份壞檔案 — 2026-11-16

> 後續（2026-11-18）：本 plugin 已不再隨 skill 附腳本。下文提到的 checker 與 `scripts/` 路徑均已移除，其職責改由回合內的命令與閱讀承擔 —— 事故的教訓不變，當時的修正手段已過時。


## 事件

delta refresh 完成後，對每個 unit 逐一執行 `python3 scripts/check_agents_md.py crates/<unit>`，九個 unit
全部回報 `cited file does not exist`。九份 `AGENTS.md` 的跨 member 引用（`crates/<other>/src/…`、
`scripts/…`）在磁碟上都存在。把命令改為在 repo root 執行 `check_agents_md.py .`，同一批檔案 exit 0，
零錯誤，九個 unit 一個都沒有壞。

## 指引

- 當時遵守的原文（`c4e1b53`）：`skills/study/SKILL.md:256` —「Mechanical
  (`scripts/check_agents_md.py <project_root>`, exit 0)」
- 當時的讀法：skill 全篇以 unit 為工作單位，`<project_root>` 只在總覽出現一次，於是它被讀成「你正在
  處理的那個目錄」——要驗一個 unit，就對那個 unit 跑。
- 形態：misleading rule

缺的是「root 同時是引用解析的基準」這一句，它在 1.2.0 不存在；文件只寫了參數叫 root，沒寫 root 決定
什麼。

## 反模式

### AP-001 · 閘門在比它要驗的引用更窄的 root 上跑

- 觸發：一個檢查工具既決定掃描範圍，又決定相對路徑的解析基準
- 錯誤動作：把工具指向被檢查的子目錄，讓它順便負責解析跨目錄引用
- 為何看起來合理：工作單位就是子目錄，指向更上層看起來像在驗別人的東西，而錯誤訊息本身不帶 root
- 正確動作：先查清工具用哪個參數解析引用，用那個目錄當 root；輸出若含檔頭，逐條歸屬到檔頭下的檔案
- 可觀察徵兆：一整批檔案出現同質錯誤（全是「引用的檔案不存在」），而肉眼可見引用存在
- 來源：2026-11-16 pdd:study 在 uniterra-dev 的 delta refresh

## 改進

**改進類別**：資訊改進

改進（步驟次序沒有產生這個失效，驗證步驟本身是對的）

## 回歸判準

下一次對多個 unit 跑檢查器時，命令列上的 root 是 repo root 而不是 unit 路徑，且輸出若仍有錯誤會先歸屬到
檔頭下的檔案再判斷；若同一批檔案又出現同質的「引用不存在」錯誤，判未修好。
