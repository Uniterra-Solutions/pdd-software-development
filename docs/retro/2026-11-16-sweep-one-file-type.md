# 刪除前的掃描只看 `.md`，刪掉了另一個工具在讀的檔案 — 2026-11-16

> 後續（2026-11-18）：本 plugin 已不再隨 skill 附腳本。下文提到的 checker 與 `scripts/` 路徑均已移除，其職責改由回合內的命令與閱讀承擔 —— 事故的教訓不變，當時的修正手段已過時。


## 事件

archive 收尾執行 reference sweep（`git grep … -- '*.md'`），一份 roster `.tsv` 未被掃到。該檔案是 plan
目錄裡的產物，被一個與 plan 無關的檢查腳本解析。它隨 plan 一起刪除後，檢查腳本在下一次執行時因找不到
檔案而失敗，而錯誤訊息指向腳本，不指向那次刪除。

## 指引

- 當時遵守的原文（`c4e1b53`）：`skills/archive/references/deletion.md:18` —「git grep -n --fixed-strings
  '<plan path>' -- '*.md' ':!docs/history/*'」
- 當時的讀法：掃描的目的是找「還在指向 plan 的文件」，而文件就是 `.md`，於是 glob 寫成 `*.md` 就等於
  「所有引用」。
- 形態：misleading rule

## 反模式

### AP-005 · 刪除前的掃描只覆蓋一種檔案類型

- 觸發：要刪除一個目錄或一批檔案，先檢查還有誰引用它
- 錯誤動作：用符合「文件」直覺的副檔名做掃描，並把結果當成完整的引用集合
- 為何看起來合理：被刪的是文件，引用它的也是文件；其他類型看起來與「引用」無關
- 正確動作：掃描全部 tracked 檔案類型；把命中分成「指向它的連結」與「讀取它的工具」兩類，後者先移到
  讀取者旁邊的穩定位置並重跑該工具，再刪
- 可觀察徵兆：刪除後某個檢查腳本開始回報缺檔，而它與被刪目錄看起來沒有關係
- 來源：2026-11-16 pdd:archive 在 uniterra-dev 的收尾

## 改進

**改進類別**：提示改進

**未採用**：代碼改進（掃描是一條命令，沒有腳本擁有它；把 glob 寫進腳本只是把同一條規則搬家，仍需要
人判斷命中的種類）；資訊改進（agent 知道 `.tsv` 存在，缺的是「引用集合依工具定義，不依副檔名」這條
規則）；流程改進（刪除步驟的次序正確，缺的是掃描範圍的定義）

## 回歸判準

下一次 archive 刪除前，掃描命令不帶 `*.md` 這類副檔名限定，且報告列出「被其他工具讀取」的檔案與它的
新位置；若刪除後仍有檢查器因缺檔而失敗，判未修好。
