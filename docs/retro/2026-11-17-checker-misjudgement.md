# AP-006 · 把工具誤判寫成流程繞道

| Field | Value |
| --- | --- |
| 技能 | `pdd:implement` |
| 階段 | 一次基線檢查在正確的樹上回報紅 |
| 觸發者 | owner：「你回歸掉所有變更幹嘛」之前的一輪自主判斷 |
| 反模式 | AP-006 |

## 一句話

一次大規模改名之後，一支基線檢查腳本回報「基線不同」並 exit 1——但被凍結的每一個值都還在，只有路徑移動了。我沒有改那個判定，而是在任務的 runbook 裡寫了一段手工繞道。

## Shape（技能的 Step 1 分類）

**形狀**：誤導性規則（misleading rule）

指引（`skills/decompose/references/ownership-rules.md:28`）：

> **Verification owns model paths only.** It may not list a production file, and it does not fix what it

當時的讀法：「那支檢查器不是我的 owned file，所以我只能調整步驟。」這把**所有權**（誰可以改那個檔）讀成**判定權**（那個判定是否為真）。句子講的是寫入權限，我拿它當成「不准質疑工具」。

## Step 2 — 反模式

```
### AP-006 · 把工具誤判寫成流程繞道

- 觸發：一個 gate 在自己的判定語意上出錯，而正確的比較鍵已經在同一段程式裡算好了
- 錯誤動作：在 runbook 裡補一段手工繞道（保存／複製／比對／還原），工具本身不動
- 為何看起來合理：改文件的步驟風險最低；工具被當成既有事實，而不是可修的產物
- 正確動作：先問「這個工具宣告的事情是真的嗎」；不真就改它的判定鍵，再把 runbook 還原成一行
- 可觀察徵兆：任務檔出現「先把 X 複製到暫存目錄… 最後用版本控制還原」的保存／還原舞蹈
- 來源：一次多步遷移
```

## Step 3 — 類別

**改進類別**：代碼改進

**未採用**：`提示改進`（gate 無人值守，句子擋不住錯誤的 exit code）、`資訊改進`（事實已在同一個流程的報告裡）、`流程改進`（單一判定鍵的錯誤，沒有重排能讓位元組比較變成正確的鍵）

## 落地

判定鍵改為語意鍵；三重控制（同一棵樹 0、只移動路徑 0、改一個值 1）。同時在 `skills/implement/references/subagent-charter.md` 的邊界條下加註：**邊界限制的是寫入，不是質疑**。

## 回歸判準

一次只移動路徑、不改任何凍結值的變更必須 exit 0 並說明「按多重集重現」；改掉任一個值必須 exit 1 並指名。任務檔若再出現保存／還原舞蹈，就是復發。
